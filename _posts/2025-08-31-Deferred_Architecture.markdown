좋은 질문이에요. 정확히는 Deferred Architecture(지연/이연 처리 아키텍처) 입니다. 은행·결제 시스템에서 실시간 요청은 얇게 처리하고, 무거운 후속 업무는 나중(배치/큐)으로 미루는 방식이고, 이를 안전하게 굴리기 위해 비동기(asynchronous) 메시징을 적극 사용합니다. 아래에 개념→왜 쓰는가→대표 시나리오→설계 패턴→운영 체크리스트 순서로 정리했어요.

## 1) 개념 한 줄 요약

* __Deferred Architecture__: 트랜잭션의 **핵심(불가역/원장 기록)**만 즉시 확정하고, 나머지 **부가 작업(정산, 보고, 수수료, 이자, 반사고처리 등)**은 큐/배치로 이연.

* __비동기 처리__: 서비스 간 호출을 메시지/이벤트로 decouple 하여 대기 없이 흘려보내고, 재시도·백프레셔로 안정성 확보.

키워드: 최소동기, 최대비동기 / 원장 일관성 보장 / 이벤트 주도 / 재처리 가능성, 멱등성

## 2) 왜 이렇게 설계하나?

1. __확장성/성능__: 실시간 경로는 짧게 → TPS↑, 지연↓. 무거운 AML·리포팅·정산은 뒤로.

1. __격리/복원력__: 외부망(MQ·Kafka·파일 교환) 장애 시에도 요청을 받아 적재 → 나중에 처리.

1. __결제 특성__: 카드/ACH/지로 등은 승인(Authorize) ↔ **정산/청구(Clearing/Settlement)**가 본질적으로 시간차가 남.

1. __업무 캘린더__: 이자계산/수수료/명세서/회계전표는 EOD/SOD 배치가 적합.

## 3) 대표 시나리오로 이해하기
### (A) 카드 결제 흐름

1. __승인(Authorization)__ — 실시간, 수 초 내

    * 가용한도 차감(메모 포스트), 리스크 스코어 최소 체크

    * 원장에 최소 레코드와 이벤트 발행(“승인됨”)

1. __정산(Clearing)__ — D+0~D+2, 파일/네트워크 도착 시

    * 금액 확정, 환율/수수료 확정 → 본 포스트

1. __청구(Posting/Billing)__ — 주기(월말)

    * 수수료·포인트·명세서 생성(전부 이연/배치)

__보상(Compensation)__: 승인만 있고 정산 불발 → 승인취소(VOID). 정산 후 오류 → 환불(Refund). (→ SAGA 보상 트랜잭션과 궁합)

### (B) 이체(ACH/대량이체)

* 접수(온라인): 형식/계좌 검증까지만 동기 승인, 작업큐 적재

* 컷오프 시각에 모아 파일/메시지 전송(비동기)

* 수취 응답에 따라 원장 최종 반영 및 반송 처리(이연)

### (C) 원장/회계

* 거래시점엔 거래원장만 확정 (append-only, double-entry)

* 회계 전표 분개/집계는 EOD 배치로 생성 → GL 시스템 반영

## 4) 설계 패턴(핵심 기술 포인트)
### 4.1 커맨드 얇게, 이벤트 두껍게

* 온라인 API는 거래 식별자, 최소 필수 검증, 원장 기록까지만 처리

* 그 결과를 이벤트로 발행(TransactionRecorded) → 후속 파이프라인이 구독하여 AML, 알림, 회계, 리포팅 수행

### 4.2 메시징 인프라

* 브로커: IBM MQ, Kafka 등

* 전달 보장: at-least-once(현실적) + 멱등성으로 중복 안전

* 백프레셔: 소비자 처리량 초과 시 큐 적체로 흡수, 스케일 아웃

### 4.3 멱등성(Idempotency) & 재시도

* Idempotency-Key(요청/이벤트 Key) + 처리 로그(outcome 테이블)로 중복 처리 무해화

* 소비자(컨슈머) 로직은 upsert / ON CONFLICT로 안전하게

### 4.4 Outbox & 트랜잭셔널 이벤트

* 같은 DB 트랜잭션에서 
* (1) 원장 기록, 
* (2) Outbox 테이블에 이벤트 저장 → 커밋 별 워커가 Outbox→브로커로 전송 → 이벤트 유실/이중커밋 문제 방지

### 4.5 상태기계 & SAGA 보상

* 단계별 상태: PENDING → AUTHORIZED → CAPTURED → POSTED → BILLED

* 실패 시 역순 보상: POSTED면 REVERSAL/REFUND, AUTHORIZED면 VOID

* 오케스트레이터(또는 코레오그래피)로 이연 단계를 안정적으로 굴림

### 4.6 일관성 모델

* 최종적 일관성(Eventual consistency) 채택

* 사용자 화면엔 “처리중/보류(PENDING)” 표시, 필요한 경우 메모 포스트/가용잔액으로 UX 보정

* 조회 API는 “원장 잔액 vs 가용 잔액”을 명확히 구분해 제공

### 4.7 배치/스케줄

* EOD/SOD/중간배치: 이자·수수료·분개, 외부 네트워크 정산

* 컷오프 타임과 영업일 달력(휴일/달말) 반영, DST 전환 고려

## 5) 간단한 아키텍처 스케치(논리)
```less
[채널(모바일/ATM/POS)]
        |
        v
[API 게이트웨이] --(동기)-> [거래 서비스(얇게)]
        |                         |
        |                         +-- 트랜잭션 DB(원장 최소 기록, Outbox 기록)
        |                                   |
        |                                   v
        |                          [Outbox 워커] --(비동기)-> [MQ/Kafka 토픽]
        |                                                       |
        |                              +------------------------+-------------------+
        v                              v                        v                   v
[즉시 응답]                    [AML/리스크]            [정산/청구]          [회계/보고]
                                          \                /                      /
                                           \              /                      /
                                            +----(상태 업데이트/보상)-----------+
```

## 6) 엔드투엔드 예시(의사코드)

```pseudo
// 동기 경로: 최소 확정
POST /transfers
 - 입력 검증(계좌 형식/잔액≥금액/제한 체크)
 - 트랜잭션 시작
   - ledger.append(debit A, credit suspense)   // 불가역 원장 기록
   - outbox.insert(TransferRecorded {txId, ...})
 - 커밋
 - 202 Accepted + txId 반환   // 처리는 계속됨(비동기)

// 비동기 워커(정산 파이프라인)
on TransferRecorded(txId):
  try:
    if amlScreening(txId) == HIT: raise AML_HIT
    settle(txId)                      // 외부망/상대은행 등 연동
    ledger.append(debit suspense, credit B)  // 본 포스트
    publish(TransferSettled {txId})
  catch transient_error: retry/backoff
  catch AML_HIT or unrecoverable:
    compensate(txId)                  // 보상: 원장 반대분개(리버설), 고객 알림
```

## 7) 운영 체크리스트

* 데이터 모델

    * 원장은 append-only, 이중기장(double-entry), 불변 레코드

    * 가용잔액 vs 원장잔액 분리

* 신뢰성

    * Outbox/Idempotency 구현, 재처리 플레이북(dead-letter) 준비

    * 순서 보장이 필요한 토픽은 파티셔닝 키 설정(계좌ID 등)

* 모니터링

    * 단계별 체류 시간 SLA(승인→정산, 정산→청구)

    * 큐 적체·재시도율·보상 트랜잭션 비율 알림

* 규정/감사

    * 모든 변경은 감사 로그(누가/언제/무엇을/왜)

    * 컷오프·영업일 달력·DST 시나리오 테스트

* UX

    * “보류/처리중” 상태 노출 정책

    * 실패/보상 시 고객 알림, 약관·명세서 반영

## 8) 언제 동기/비동기를 나누나? (실무 기준)

* __동기 필수__: 고객 잔액/한도 영향 즉시 반영, 중복 과금 방지, 강한 승인 필요(예: 카드 승인, 이체 접수)

* __비동기 적합__: 외부 네트워크 왕복, 대량 계산(이자/수수료/보고), 회계 전표, 알림/포인트, 정산/청구
